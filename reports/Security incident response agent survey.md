# Every stage exists; nobody closes the loop

No maintained open-source project runs the whole loop the planned agent needs, from a new advisory through an exposure verdict, a mitigation or verified patch and a standards-based report to a page, yet every stage already has solid reusable parts, so the hackathon's real job is to compose them and close the loop rather than to invent any single stage. The closest prior art covers two or three stages each: NVIDIA's Vulnerability Analysis blueprint decides whether a CVE is exploitable in a container image and writes a VEX-style verdict but never patches; RAPTOR pairs mechanical reachability with a fix planner, CycloneDX VEX and a native Mistral provider; OWASP dep-scan contributes deterministic reachability for seven ecosystems, CSAF VEX and an MCP server; and cve-intel enriches CVEs from dozens of feeds and fires webhooks but stops at rule-written runbooks. At least four tiny repositories pushed in October and November 2026, two of them Meta hackathon entries, already chase the same loop with the same recipe, so the idea is timely but judges may have seen its usual shape. The architecture that holds up hands every verifiable fact to a deterministic tool (OSV, GHSA, KEV and EPSS feeds, Dependency-Track webhooks, osv-scanner and govulncheck, `osv-scanner fix` and Copacetic, vexctl, CISA's SSVC table, PagerDuty) and keeps Mistral models for reading advisories, gathering evidence, judging ambiguous cases and writing, with Mistral Vibe's headless mode making the code changes. Evaluation is where the team can add something new: no mature public benchmark scores whether a given project is affected by a given CVE, so a hand-labelled set of 30 to 60 project-advisory pairs is itself a contribution, while PatchEval-Verified (230 Dockerized Go, JavaScript and Python CVEs, with no Mistral model on its leaderboard) measures patching. The strongest demos are React2Shell on a one-command vulhub target and the May 2026 Mini Shai-Hulud wave that trojanized Mistral's own npm and PyPI SDKs, replayed from fixture lockfiles. The gaps worth owning are fleet-wide layered exposure checks, evidence-carrying OpenVEX, escalation policy written as code, verified upgrade PRs and a supply-chain compromise playbook, all running on self-hostable Mistral models.

## The nearest prior art stops after two or three stages

A survey of open-source repositories, with stars, licenses and activity checked through the GitHub API on 21 November 2026, found only a handful that take an advisory as input and decide exposure for a specific artifact with an LLM in the loop. The most sophisticated is **NVIDIA's Vulnerability Analysis blueprint** (255 stars, Apache-2.0), the successor to Agent Morpheus. A CVE Researcher and a Container Analyzer run in parallel, an Exploitability Analyzer weighs their evidence, and a VEX Categorizer returns `affected` or `not_affected` with a justification such as `code_not_reachable` or `requires_configuration`, falling back to `unknown` rather than treating a failed analysis as safe. Deterministic pre-triage settles clear-cut cases before any deep LLM call, and a FastAPI service exposes async jobs and HMAC-signed completion webhooks ([NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). The blueprint handles containers only, needs NVIDIA NIM or a compatible endpoint plus a Tavily key and 20 GiB of disk, does no patching or ticketing, and never says its VEX JSON follows OpenVEX, CSAF or CycloneDX ([NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). Its 2024 predecessor used about **41 LLM queries per CVE** and cut a 20-CVE container from 2,842 to 305 seconds through parallelism, with analysts approving each VEX before publication ([NVIDIA technical blog](https://developer.nvidia.com/blog/applying-generative-ai-for-cve-analysis-at-an-enterprise-scale/)). For a hackathon the blueprint is better mined than run: its decision chain (association, code presence, execution path, trigger conditions, protective controls) and its fail-safe `unknown` translate directly into prompts for a Mistral model.

**RAPTOR** (4,042 stars; MIT according to its README, although GitHub's API records no license assertion) is the strongest single building block for the assess and plan-fix stages. Its SCA workflow matches dependencies against OSV, KEV and EPSS, runs two-tier reachability (imports first, then function-level calls when the advisory names affected symbols) and writes a CycloneDX 1.5 SBOM with a VEX block plus SARIF; the docs stress that reachability is computed mechanically and that the later LLM review is never the source of truth ([RAPTOR SCA docs](https://github.com/gadievron/raptor/blob/main/docs/sca.md)). `raptor-sca fix` shows or applies a fix plan with switches such as `--cve-only` and `--allow-major` ([RAPTOR SCA docs](https://github.com/gadievron/raptor/blob/main/docs/sca.md)), and RAPTOR is the only vulnerability agent in the survey with a **native Mistral provider**, keyed by `MISTRAL_API_KEY` and defaulting to `mistral-large-latest` ([RAPTOR LLM docs](https://github.com/gadievron/raptor/blob/main/docs/llm.md)). Its README admits the code is unpolished, largely AI-generated and still exposed to prompt injection ([RAPTOR README](https://github.com/gadievron/raptor#readme)). **OWASP dep-scan** (1,462 stars, MIT) has no LLM inside but is the most complete deterministic exposure engine: reachability across seven ecosystems through four language slicers, CSAF 2.0 and 2.1 VEX output, a server mode, and an agent plugin with 14 skills that launches `depscan mcp` ([dep-scan README](https://github.com/owasp-dep-scan/dep-scan#readme); [dep-scan agent plugin](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/README.md)). The plugin ships instructions rather than logic, and because the MCP server has no tool for recording a triage decision, its triage sub-agent cannot write a verdict back ([dep-scan agent plugin](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/README.md)).

Around these sit smaller tools that each nail one idea. **OWASP Xpsd** is a reachability agent that navigates code with ast-grep, fetches the advisory and fixing commit through OSV, and attaches a rationale, an entry-point-to-sink call path and evidence links to every alert, with a CI gate that fails builds on reachable findings; it spends one agent session per finding, so cost grows with the alert count ([Xpsd README](https://github.com/OWASP/Xpsd#readme)). **cve-intel** (151 stars, Rust) queries up to 46 sources, returns a 0–100 risk score, keeps a decision ledger exportable as OpenVEX or CycloneDX VEX, answers which machines carry a CVE in fleet mode with Slack and Mattermost webhooks, and exposes **42 MCP tools**, but its runbooks come from fixed rules with no AI and it opens no pull requests ([cve-intel README](https://github.com/Fazmin/cve-intel#readme)). **Fathometer** offers a ready escalation vocabulary of Escalate, Act, Watch and Noise, where each downgrade names the missing precondition and CVSS, EPSS and KEV act as weights rather than verdicts, yet it deliberately sends no notifications ([Fathometer README](https://github.com/THEKROLL-LTD/Fathometer#readme)). vens has an LLM score each CVE against a system-context file and emits CycloneDX VEX ([vens README](https://github.com/venslabs/vens#readme)), while vexllm, the minimal LLM-to-OpenVEX tool, is archived ([vexllm README](https://github.com/AkihiroSuda/vexllm#readme)).

The high-star AI-security agents mostly solve a different problem. OpenAI's Codex Security CLI (14,239 stars), Visa's VVAH (3,098) and Google's Mantis (2,815) hunt new bugs in first-party code rather than respond to published advisories. Their validate-and-patch stages are useful patterns, but Codex Security offers no Mistral route, VVAH's fix validation runs no tests, and Mantis warns that it belongs only in isolated environments ([Codex Security README](https://github.com/openai/codex-security#readme); [VVAH README](https://github.com/visa/visa-vulnerability-agentic-harness#readme); [Mantis README](https://github.com/google/mantis#readme)). Patchwork (1,580 stars, AGPL-3.0) supplies PR-creation and Slack steps plus a dep-scan-driven upgrade flow, but documents no test-based verification ([Patchwork README](https://github.com/patched-codes/patchwork#readme)). Several once-prominent options are poor foundations: Alias Robotics' CAI framework was archived in August 2026 in favour of a commercial successor, and Anthropic's reference defence harness says it is not maintained ([CAI README](https://github.com/aliasrobotics/cai#readme); [Anthropic harness README](https://github.com/anthropics/defending-code-reference-harness#readme)). Closed products confirm that opening a PR for a vulnerable dependency is now a commodity. Since 7 April 2026 GitHub lets Dependabot alerts be assigned to Copilot, Claude or Codex agents that analyse the advisory and open a draft PR ([GitHub changelog](https://github.blog/changelog/2026-04-07-dependabot-alerts-are-now-assignable-to-ai-agents-for-remediation)), Snyk's Evo Remediation Agent runs its fix loop autonomously and queues build-breaking fixes for approval ([Snyk](https://snyk.io/news/snyk-launches-evo-agentic-appsec/)), and Google's CodeMender preview runs a proof of concept in a customer sandbox before proposing a fix ([Help Net Security](https://www.helpnetsecurity.com/2026/07/24/google-codemender-ai-agent-code-security/)).

The finding that matters most for a hackathon team is that the full loop is already being attempted at small scale. **Patchwarden** (zero stars, no license) fires when a new CVE feed entry lands, sends OSV-Scanner, Trivy and Syft output to a Claude triage step, lets a deterministic policy gate choose between auto-fix and human review, and ships either a smallest-safe dependency bump or a Copacetic image patch, verified by re-scan and tests and signed with Cosign; it has no VEX and no paging ([Patchwarden README](https://github.com/deenojo/Vulnerability-Remediation-Agent#readme)). vexproof emits OpenVEX from verified Python call paths and AutoPatch opens a PR only after a three-gate sandbox check, and both came out of the Meta Global AI Developer Hackathon that ended on 4 November 2026 ([vexproof README](https://github.com/henrymbuguak/vexproof#readme); [AutoPatch README](https://github.com/Kokenya/autopatch#readme)). cve-triage-agent turns NVD, EPSS and KEV data into an SSVC decision and skips the LLM entirely when Python AST analysis shows the vulnerable code is unreachable ([cve-triage-agent README](https://github.com/singhalkapil/cve-triage-agent#readme)), and WaarlandIT's cve-agent covers NVD polling, assessment, Markdown reports and Slack alerts without patching ([cve-agent README](https://github.com/WaarlandIT/cve-agent#readme)). All of them converge on one recipe of deterministic signals, LLM judgment, re-scan or test verification and a policy gate, so the recipe alone will not stand out; closing the whole loop with standard evidence, explicit escalation and Mistral-native execution can.

## Deterministic tools already supply the facts at every stage

The designs that earn trust share one rule: the model recommends, and deterministic code or a person decides. NVIDIA settles clear cases without deep LLM calls, RAPTOR computes reachability without consulting a model, Patchwarden's policy gate rather than its agent decides what ships, and PatchTriage never lets AI choose the SSVC outcome ([NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme); [RAPTOR SCA docs](https://github.com/gadievron/raptor/blob/main/docs/sca.md); [Patchwarden README](https://github.com/deenojo/Vulnerability-Remediation-Agent#readme); [PatchTriage README](https://github.com/d01ki/PatchTriage#readme)). The reuse map below follows that rule, assigning each verifiable fact to an existing tool and keeping Mistral for the work that needs reading and judgment; the subsections after it give the evidence for each row.

| Stage | Reuse first | Where Mistral adds value | Watch out for |
|---|---|---|---|
| Ingest | OSV bulk exports and `querybatch`; GHSA REST (`affects`, `type=malware`); KEV JSON; EPSS API; push from GitHub's `security_advisory` and `dependabot_alert` webhooks or Dependency-Track v5 | Turning advisory prose into affected symbols, preconditions and fixed versions | NVD no longer enriches most new CVEs, so CPE matching misses them; join on purl |
| Assess | syft or cdxgen SBOMs; osv-scanner, Grype or Trivy matching; govulncheck (Go), `osv-scanner --call-analysis`, dep-scan, Jelly; nuclei on owned live services | Tool-using reachability with call-path evidence; configuration and deployment conditions | Every reachability tool has blind spots; a negative nuclei scan proves little; sandbox tools that run project code |
| Mitigate and patch | `osv-scanner fix`, `pip-audit --fix`, `cargo audit fix`, Renovate or Dependabot; Copacetic for images; CrowdSec virtual-patch rules; pinact or ratchet for Actions | Mistral Vibe headless edits, breaking-upgrade repair, backports, draft WAF rules | About one in five fully validated patches is still semantically wrong; transitive and major-version support is partial |
| Report | vexctl or go-vex (OpenVEX); dep-scan (CSAF); CycloneDX VEX; SecObserve or DefectDojo as the findings hub | Incident narrative, impact statement, timeline | VEX status, KEV and EPSS fields must come from tools, never from the model |
| Escalate | SSVC table (`certcc-ssvc`, `ssvc`); KEV due dates; PagerDuty Events v2 with `dedup_key` or GoAlert; hosted Slack and Atlassian MCP; GitHub issues | Evidence for each SSVC decision point; ticket and page text | Dispatch and Grafana OnCall OSS are archived; Opsgenie shuts down in April 2027 |

### Ingest means polling, with a few push exceptions

The open vulnerability data layer is rich but almost entirely pull-based. OSV.dev serves a query API with no stated rate limit and bulk exports whose `modified_id.csv` lists changes newest-first, so a poller can stop at the last timestamp it saw, but it offers no push mechanism ([OSV API docs](https://google.github.io/osv.dev/api/); [OSV data docs](https://google.github.io/osv.dev/data/)). The GitHub Advisory Database REST endpoint checks up to **1,000 `package@version` strings** in one `affects` query and returns malware advisories only when asked with `type=malware` ([GitHub REST docs](https://docs.github.com/en/rest/security-advisories/global-advisories)). The CVE List V5 repository refreshes about every seven minutes with a rolling `deltaLog.json` ([cvelistV5 README](https://github.com/CVEProject/cvelistV5)), the KEV mirror updates during US weekday business hours ([cisagov/kev-data](https://github.com/cisagov/kev-data)), and EPSS is a simple batch API ([FIRST EPSS API](https://api.first.org/epss)). Push triggers are scarce. GitHub's `security_advisory` webhook is available only to GitHub Apps, while `dependabot_alert` works per repository or organization ([GitHub webhook docs](https://docs.github.com/en/webhooks/webhook-events-and-payloads)); OpenCVE and CIRCL's Vulnerability-Lookup send email or webhook alerts for vendor and product watchlists, which suits appliances better than SBOMs ([OpenCVE](https://github.com/opencve/opencve); [Vulnerability-Lookup](https://github.com/vulnerability-lookup/vulnerability-lookup)). The best SBOM-aware trigger is **Dependency-Track v5**, now GA with v4 reaching end of life in December 2026, which fires NEW_VULNERABILITY, NEW_VULNERABLE_DEPENDENCY and VEX_CONSUMED notifications to webhooks, Slack, Jira, Kafka and others, scoped by project tag and an optional CEL filter ([Dependency-Track README](https://github.com/DependencyTrack/dependency-track); [notification groups](https://github.com/DependencyTrack/docs/blob/main/docs/reference/notifications/groups.md); [publishers](https://github.com/DependencyTrack/docs/blob/main/docs/reference/notifications/publishers.md); [notification concepts](https://github.com/DependencyTrack/docs/blob/main/docs/concepts/notifications.md)). That allows a tidy closed loop in which CI uploads a CycloneDX SBOM, Dependency-Track's webhook calls the agent, and the agent's VEX upload raises VEX_CONSUMED, although the exact v5 webhook payload has not been verified.

One 2026 change dictates the join key. Since April 2026 NIST enriches only CVEs that are in KEV, affect software the federal government uses, or fall under EO 14028's critical-software definition; the rest are marked not scheduled and get **no NVD CVSS score and no CPE** ([Socket blog](https://socket.dev/blog/nist-officially-stops-enriching-most-cves)). CPE-keyed matchers will therefore miss more new CVEs, so the agent should match on purl ranges from OSV and GHSA and read severity from the CNA's CVSS, the SSVC decision points CISA's Vulnrichment adds to CVE records, KEV and EPSS ([cisagov/vulnrichment](https://github.com/cisagov/vulnrichment)). Supply-chain signals come from GHSA's malware type and OpenSSF's malicious-packages repository, which OSV ingests as MAL- records ([ossf/malicious-packages](https://github.com/ossf/malicious-packages); [OSV data docs](https://google.github.io/osv.dev/data/)). Maintained MCP servers already wrap part of this layer: GitHub's official server exposes `security_advisories` and `dependabot` toolsets, osv-scanner ships an experimental MCP mode, Stacklok's osv-mcp wraps raw OSV lookups, and vulnify folds CVE, NVD, KEV, EPSS and OSV data into one SQLite database behind an MCP server ([github-mcp-server](https://github.com/github/github-mcp-server); [osv-scanner MCP command](https://github.com/google/osv-scanner/blob/main/cmd/osv-scanner/mcp/command.go); [osv-mcp](https://github.com/StacklokLabs/osv-mcp); [vulnify](https://github.com/mez-0/vulnify#readme)). Anchore's official grype-mcp is archived and the most-starred Dependency-Track MCP describes itself as vibe-coded ([grype-mcp](https://github.com/anchore/grype-mcp); [dependency-track-mcp](https://github.com/secprog/dependency-track-mcp)), so thin custom wrappers over govulncheck, vexctl and the Dependency-Track REST API are safer than adopting community servers.

### Version matching is solved; reachability is still per-language

Deciding whether a vulnerable package is present at an affected version is commodity work. syft or cdxgen produce CycloneDX or SPDX SBOMs, and osv-scanner (11,579 stars), Grype and Trivy (39,586 stars) match them and emit JSON and SARIF; osv-scanner reads lockfiles from 13 language ecosystems and can scan against downloaded databases when package lists must not leave the network ([osv-scanner README](https://github.com/google/osv-scanner); [osv-scanner output docs](https://google.github.io/osv-scanner/output/); [Grype README](https://github.com/anchore/grype)). Trivy accepts OpenVEX and CSAF documents and Grype takes VEX through `--vex`, so the agent can prove a verdict took effect simply by re-running the scan ([Trivy VEX docs](https://trivy.dev/latest/docs/supply-chain/vex/file/); [Grype README](https://github.com/anchore/grype)). Reachability is where coverage fragments by language. Go is best served: **govulncheck** filters findings through the call graph and writes OpenVEX directly ([govulncheck docs](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck)). osv-scanner's `--call-analysis` covers Go and Rust, with Rust running build scripts, and gained Java JAR reachability in v2.2.2 ([osv-scanner flags](https://github.com/google/osv-scanner/blob/main/cmd/osv-scanner/internal/helper/flags.go); [osv-scanner changelog](https://github.com/google/osv-scanner/blob/main/CHANGELOG.md)). dep-scan reaches Java, JavaScript, Python, PHP, Rust, Go and .NET, but its atom slicer needs Java 23 or later plus each language's toolchain ([dep-scan README](https://github.com/owasp-dep-scan/dep-scan#readme); [atom README](https://github.com/AppThreat/atom)), and Jelly provides research-grade JavaScript and TypeScript exposure analysis that can need an 8 GB heap on full dependency trees ([Jelly README](https://github.com/cs-au-dk/jelly)). The survey found no independent precision or recall figures for any of these tools, and each documents blind spots such as reflection and dynamic dispatch.

Research explains why a model still earns its place in this stage. More than **26% of vulnerable functions are not among the functions the fixing patch modifies**, so reachability keyed to the patch diff misses real exposure ([VFArchē, arXiv 2506.18050](https://arxiv.org/abs/2506.18050)); a study of 3 million Maven packages found that dependency-level reasoning inflates the count of affected projects compared with call graphs ([arXiv 2301.07972](https://arxiv.org/abs/2301.07972)); and seven VEX-producing scanners disagree with each other mainly because their databases differ ([arXiv 2503.14388](https://arxiv.org/abs/2503.14388)). Reachability is not exploitability either: NVIDIA evaluates trigger conditions and protective controls as separate steps, and Xpsd accepts a guidance input for facts the code cannot show, such as what is network-exposed ([NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme); [Xpsd README](https://github.com/OWASP/Xpsd#readme)). The hardest piece is the reason code. On VEX-Bench, frontier agents reach about **80% F1 on affected versus not affected**, but only one model clears 70% macro-F1 on the justification category ([VEX-Bench, arXiv 2609.08040](https://arxiv.org/abs/2609.08040)). The design that follows is layered: deterministic version matching, deterministic reachability wherever a tool exists, a Mistral agent with read-only code tools for the remaining languages and for configuration conditions, and `under_investigation` whenever evidence runs out. For deployed services, nuclei's community templates (3,587 tagged `cve`, 1,496 covering KEV entries) can confirm exploitability on owned and authorized targets, though a negative result proves little ([nuclei-templates README](https://github.com/projectdiscovery/nuclei-templates)). Several tools execute project code while analysing or fixing, including `osv-scanner fix`, `cargo audit` without `--file` and `npm audit fix`, so they belong in a sandbox ([osv-scanner README](https://github.com/google/osv-scanner); [cargo-audit README](https://github.com/rustsec/rustsec/tree/main/cargo-audit); [npm audit docs](https://docs.npmjs.com/cli/v11/commands/npm-audit)).

### Fixes go deterministic first, agentic second, verified always

For dependency and image CVEs, a scriptable deterministic toolchain should be the first resort. **`osv-scanner fix`** resolves the full transitive graph through deps.dev, ranks direct upgrades by how many vulnerabilities each removes, caps the semver jump per package with `--upgrade-config`, targets specific advisories with `--vulns` and reports in JSON, but it is experimental and covers only npm and Maven ([osv-scanner guided remediation](https://github.com/google/osv-scanner/blob/main/docs/guided-remediation.md)). Renovate's OSV mode raises fix PRs for direct dependencies only, uv projects excepted, and its vulnerability fixes default to the lowest fixed version ([Renovate docs](https://github.com/renovatebot/renovate/blob/main/docs/usage/configuration-options.md)); Dependabot fixes transitive dependencies properly only in npm and NuGet and never runs your tests, offering compatibility scores from other repositories' CI instead ([Dependabot docs](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/about-dependabot-security-updates)). `pip-audit --fix` and `cargo audit fix` cover Python and Rust ([pip-audit README](https://github.com/pypa/pip-audit); [cargo-audit README](https://github.com/rustsec/rustsec/tree/main/cargo-audit)). For running containers, **Copacetic** (1,760 stars) patches an image in place from a Trivy report without a rebuild, third-party images included, with experimental pip, npm and Go-module patching ([Copacetic README](https://github.com/project-copacetic/copacetic); [app-level patching docs](https://github.com/project-copacetic/copacetic/blob/main/website/docs/app-level-patching.md)).

When no fix can ship yet, mitigation engines exist but rule generation does not. CrowdSec's hub carries per-CVE virtual-patch rules named `vpatch-CVE-…` that install with one command and are built for near-zero false positives, alongside mature engines such as OWASP CRS, Coraza and ModSecurity ([CrowdSec docs](https://docs.crowdsec.net/docs/appsec/vpatch_and_crs)). No mature open-source tool turns an advisory into a validated WAF rule; the one small LLM attempt, WAFSmith, has gone stale ([WAFSmith](https://github.com/tankeehock/wafsmith)). Supply-chain mitigations are deterministic and fast: pinact and ratchet pin GitHub Actions to immutable versions, harden-runner can block known-compromised packages on CI runners, and Renovate refuses updates that OSV flags as malicious ([pinact](https://github.com/suzuki-shunsuke/pinact); [ratchet](https://github.com/sethvargo/ratchet); [harden-runner](https://github.com/step-security/harden-runner); [Renovate docs](https://github.com/renovatebot/renovate/blob/main/docs/usage/configuration-options.md)). No open automation for advisory-driven feature-flag or configuration mitigations turned up at all.

For code changes, **Mistral Vibe** (Apache-2.0, 5,443 stars) is the native choice. Its programmatic mode reads a prompt file, returns JSON, enforces price, turn and time budgets, denies any tool call that needs approval unless auto-approval is switched on, accepts per-agent bash allowlists such as `pytest` and `npm test` only, and signals outcomes through five exit codes; the repository also ships a GitHub Action ([Vibe programmatic mode](https://github.com/mistralai/mistral-vibe/blob/main/docs/programmatic-mode.md); [Vibe action.yml](https://github.com/mistralai/mistral-vibe/blob/main/action.yml)). It runs Devstral 2 (123B) and Devstral Small 2 (24B), which Mistral reports at **72.2% and 68.0% on SWE-bench Verified** ([Mistral announcement](https://mistral.ai/news/devstral-2-vibe-cli/)), and VentureBeat reads Devstral 2's modified MIT license as requiring a commercial license for companies above $20M in monthly revenue ([VentureBeat](https://venturebeat.com/ai/mistral-launches-powerful-devstral-2-coding-model-including-open-source)). Vibe's repository contains an `.agents/skills` tree, which suggests, though no documentation confirms it, that dep-scan's 14 skills or Trail of Bits' triage, CVSS and patch-validation skills could load directly ([Vibe skills tree](https://github.com/mistralai/mistral-vibe/tree/main/.agents/skills); [trailofbits/skills](https://github.com/trailofbits/skills#readme)). Goose lists Mistral as a native provider, and Aider and OpenHands reach it through LiteLLM or their bring-your-own-model settings ([Goose providers](https://github.com/aaif-goose/goose/blob/main/documentation/docs/getting-started/providers.md); [Aider LLM docs](https://github.com/Aider-AI/aider/blob/main/aider/website/docs/llms/other.md); [OpenHands README](https://github.com/OpenHands/OpenHands)).

The evidence on agent-written security patches argues for heavy verification. Team Atlanta ran off-the-shelf Claude Code, Codex CLI, Gemini CLI and Copilot CLI against 63 crashes from the AIxCC final: the best configuration fixed about 71% and the weakest about 57%, a three-agent ensemble beat every single agent, and **about 20% of the best configuration's validated patches were semantically wrong**, most often because they altered functionality or patched the symptom ([Team Atlanta](https://team-atlanta.github.io/blog/post-patch-2026-ensemble/)); the AIxCC SoK found semantic issues in 37.7% and 45.6% of patches from two configurations ([SoK, arXiv 2602.07666](https://arxiv.org/html/2602.07666v1)). The open AIxCC systems, including Buttercup's laptop-scale standalone build, OpenSSF's OSS-CRS with LiteLLM routing, PatchAgent and Shellphish's PatcherY, all assume a crashing proof of vulnerability and an OSS-Fuzz-style C or Java build, so they fit a team holding a reproducer, not one reacting to an advisory against a library it imports ([Buttercup](https://github.com/trailofbits/buttercup); [OSS-CRS](https://github.com/ossf/oss-crs); [PatchAgent](https://github.com/cla7aye15I4nd/PatchAgent); [PatcherY](https://github.com/shellphish/PatcherY)). Small verification parts exist and are easy to adopt: AutoPatch requires a regression test that fails before the patch and passes after with no new suite failures ([AutoPatch README](https://github.com/Kokenya/autopatch#readme)), dvalincode re-runs scanners and tests to produce a Verified Fix Record in which no model influences the verdict ([dvalincode README](https://github.com/arthurpanhku/dvalincode#readme)), and hyrum generates tests that pin how code calls each dependency so that a bump which changes relied-upon behaviour fails ([hyrum README](https://github.com/alpha-omega-security/hyrum#readme)). Breaking upgrades stay hard: the best model in KTH's Byam study repaired 27% of build failures caused by 103 breaking Java dependency updates ([arXiv 2505.07522](https://arxiv.org/abs/2505.07522)). A sound gate runs the build, the existing tests, a scanner re-run, PoC replay where one exists and an LLM root-cause critique, and still routes major bumps, unfixable transitive vulnerabilities and patches without a reproducer to a person.

### OpenVEX carries the verdict while Mistral writes the story

All three VEX dialects encode exactly the agent's verdict space. **OpenVEX** is the leanest, with four statuses and five justifications; a `not_affected` statement must carry a justification or an impact statement, and the spec discourages free-text impact statements in automated systems ([OpenVEX spec](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md)), while `vexctl` creates, merges, validates and attests documents ([vexctl README](https://github.com/openvex/vexctl)). CycloneDX VEX (schema 1.7, latest release 1.7.2 in September 2026) is richer, with six analysis states, nine justifications and five response types ([CycloneDX 1.7 schema](https://github.com/CycloneDX/specification/blob/master/schema/bom-1.7.schema.json); [CycloneDX releases](https://github.com/CycloneDX/specification/releases)). CSAF 2.0 is the formal standard, adopted as ISO/IEC 20153, while CSAF 2.1 remains a committee draft ([ISO/IEC 20153](https://www.iso.org/standard/89986.html); [CSAF 2.1 CSD02](https://docs.oasis-open.org/csaf/csaf/v2.1/csd02/csaf-v2.1-csd02.pdf)). Today's LLM tools scatter across all of them: dep-scan writes CSAF, RAPTOR and vens write CycloneDX, cve-intel writes OpenVEX or CycloneDX, NVIDIA writes its own Markdown and JSON, and Xpsd writes SARIF instead of VEX ([dep-scan README](https://github.com/owasp-dep-scan/dep-scan#readme); [RAPTOR SCA docs](https://github.com/gadievron/raptor/blob/main/docs/sca.md); [cve-intel README](https://github.com/Fazmin/cve-intel#readme); [NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme); [Xpsd README](https://github.com/OWASP/Xpsd#readme)). OpenVEX is the pragmatic hackathon choice because Trivy and Grype both consume it, which lets the demo show a `not_affected` verdict suppressing a finding on re-scan; CycloneDX makes sense only if the pipeline already centres on Dependency-Track.

The findings record can live in an existing hub. SecObserve imports and exports VEX in CSAF, CycloneDX and OpenVEX behind a feature flag, syncs issues one way to GitHub, GitLab or Jira, and enriches findings nightly with EPSS and exploit data from KEV, Exploit-DB, Metasploit and Nuclei ([SecObserve VEX docs](https://github.com/SecObserve/SecObserve/blob/main/docs/integrations/vex.md); [issue tracker docs](https://github.com/SecObserve/SecObserve/blob/main/docs/integrations/issue_trackers.md); [exploit information docs](https://github.com/SecObserve/SecObserve/blob/main/docs/integrations/exploit_information.md)). DefectDojo (5,262 stars) deduplicates repeat findings, counts down per-severity SLAs, syncs with Jira in both directions and now has an official MCP server ([DefectDojo dedup](https://github.com/DefectDojo/django-DefectDojo/blob/dev/docs/content/triage_findings/finding_deduplication/about_deduplication.md); [SLA docs](https://github.com/DefectDojo/django-DefectDojo/blob/dev/docs/content/asset_modelling/OS_hierarchy/OS__sla_configuration.md); [Jira guide](https://github.com/DefectDojo/django-DefectDojo/blob/dev/docs/content/connectors/os_jira/os__jira_guide.md); [defectdojo-mcp](https://github.com/DefectDojo/defectdojo-mcp#readme)). For the human-readable report, the EU Cyber Resilience Act is the template driver most relevant to an EU hackathon: since **11 September 2026** manufacturers must report actively exploited vulnerabilities with an early warning within 24 hours, a notification within 72 hours and a final report within 14 days of a corrective measure, through ENISA's Single Reporting Platform ([European Commission CRA reporting](https://digital-strategy.ec.europa.eu/en/policies/cra-reporting); [ENISA](https://www.enisa.europa.eu/news/the-cra-single-reporting-platform-is-launched)). PagerDuty publishes Apache-2.0 postmortem templates ([PagerDuty postmortem docs](https://github.com/PagerDuty/postmortem-docs)), and Netflix's archived Dispatch still holds LLM functions for incident summaries and tactical reports that make a useful reference design ([Dispatch AI service](https://github.com/Netflix/dispatch/blob/main/src/dispatch/ai/service.py)). The division of labour is simple: tools fill VEX status, KEV dates and EPSS values, and Mistral drafts the summary, impact statement and timeline, citing a lockfile line, call site or advisory for every claim.

### SSVC turns page-or-ticket into a table lookup

CISA's SSVC tree is the most defensible escalation policy because it is a **fixed 36-row lookup** with four outcomes (Track, Track*, Attend and Act) over four decision points: Exploitation, Automatable, Technical Impact and Mission & Well-being ([CISA SSVC guide](https://www.cisa.gov/sites/default/files/publications/cisa-ssvc-guide%20508c.pdf)). CISA's Vulnrichment program publishes the first three for each CVE it analyses, leaving only asset criticality for the team to supply ([cisagov/vulnrichment](https://github.com/cisagov/vulnrichment)), and two maintained Python packages implement the tree, `certcc-ssvc` from CERT/CC and the MIT-licensed `ssvc` ([CERTCC/SSVC](https://github.com/CERTCC/SSVC#readme); [python-ssvc](https://github.com/Vulnesis/python-ssvc#readme)). KEV supplies urgency: the catalog held 1,790 entries on 20 November 2026, and **166 of the 306 entries added in 2026 carry a three-day due date** ([cisagov/kev-data](https://github.com/cisagov/kev-data)). A policy that fits these inputs, offered here as synthesis rather than CISA guidance, only logs when the exposure check proves `not_affected`; pages whenever an exposed production or internet-facing asset meets KEV, active exploitation or a supply-chain compromise that actually executed; and otherwise maps Act to a page plus a ticket due in about three days, Attend to a two-week ticket with a Slack notice, Track* to a watched ticket and Track to a logged VEX statement. EPSS should only break ties; CVE_Prioritizer, for example, uses 0.2 as its threshold ([CVE_Prioritizer README](https://github.com/TURROKS/CVE_Prioritizer#readme)). The model gathers evidence for each decision point, and code performs the lookup.

Delivery channels are simple and well documented. PagerDuty's Events API v2 needs only a summary, source, severity and routing key, and a stable `dedup_key` built from the CVE and service folds repeated signals into one incident that a later resolve event closes ([PagerDuty Events API v2](https://docs.pagerduty.com/developer/events-api-v2-overview); [go-pagerduty](https://github.com/PagerDuty/go-pagerduty)); PagerDuty's local MCP repository is deprecated in favour of a hosted server ([pagerduty-mcp-server](https://github.com/PagerDuty/pagerduty-mcp-server#readme)). **GoAlert** (2,882 stars, Apache-2.0) is the self-hosted equivalent, with a generic endpoint for summary, details, dedup and close actions and a demo container ([GoAlert README](https://github.com/target/goalert#readme); [GoAlert generic API](https://github.com/target/goalert/blob/master/genericapi/handler.go)). Slack's hosted MCP server works only for Marketplace or internal apps with admin approval ([Slack MCP docs](https://docs.slack.dev/ai/mcp-server/)), whereas the community korotovsky server ships with posting disabled until it is enabled for an allowlist of channels ([korotovsky slack-mcp-server](https://github.com/korotovsky/slack-mcp-server#readme)); Atlassian's hosted MCP server is generally available ([atlassian-mcp-server](https://github.com/atlassian/atlassian-mcp-server#readme)). Three dead ends are worth avoiding: Netflix Dispatch was archived in September 2025, Grafana OnCall OSS in March 2026, and Opsgenie shuts down on 5 April 2027 ([Dispatch README](https://github.com/Netflix/dispatch#readme); [Grafana OnCall README](https://github.com/grafana-cold-storage/oncall#readme); [Atlassian Opsgenie migration](https://www.atlassian.com/software/opsgenie/migration)).

Autonomy needs its own design. Wazuh-Autopilot shows the clearest open pattern: four autonomy levels from observe to autonomous, a two-person rule, and agents that never receive state-changing tools, while a separate platform executes, verifies and can roll back approved actions ([Wazuh-Autopilot README](https://github.com/gensecaihq/Wazuh-Autopilot#readme)). GitHub's seclab-taskflow-agent can require user confirmation for listed MCP tools and accepts any OpenAI-compatible endpoint ([seclab-taskflow-agent README](https://github.com/GitHubSecurityLab/seclab-taskflow-agent#readme)). A team that wants a platform rather than glue can use Tracecat (3,908 stars, AGPL-3.0), which brings cases, an MCP client and server, nsjail sandboxing and a native Mistral provider, or Shuffle, which lists Mistral among its AI providers ([Tracecat README](https://github.com/TracecatHQ/tracecat#readme); [Tracecat agent config](https://github.com/TracecatHQ/tracecat/blob/main/tracecat/agent/config.py); [Shuffle AI docs](https://github.com/Shuffle/shuffle-docs/blob/master/docs/AI.md)). Readings of Tracecat's README disagree on whether human approval of sensitive tool calls is open source or an Enterprise Edition feature, so check before depending on it. Licenses matter if the result is published: Patchwork, Tracecat, Renovate and Buttercup are AGPL-3.0, Trail of Bits' skills are CC-BY-SA-4.0, and Patchwarden and SecBench.js carry no license at all ([Tracecat LICENSE](https://github.com/TracecatHQ/tracecat/blob/main/LICENSE); [Renovate](https://github.com/renovatebot/renovate); [trailofbits/skills](https://github.com/trailofbits/skills#readme); [SecBench.js](https://github.com/cristianstaicu/SecBench.js)).

## Measure each stage separately, then demo Mistral's own breach

Published benchmarks cover the vulnerability side of the pipeline well and the response side barely at all, so the evaluation plan has to mix off-the-shelf suites with home-made sets. The table summarizes what to measure at each stage and what published numbers exist to compare against.

| Stage | Metric | Data | Published anchor |
|---|---|---|---|
| Ingest and triage | CVSS-vector and CWE accuracy; time from publication to verdict | [CTIBench](https://github.com/maveryn/cti-bench) CTI-VSP and CTI-RCM, 1,000 items each | None for latency |
| Exposure | Precision and recall on "affected"; exact justification accuracy; unknown rate under three policies | Custom 30–60 pairs; [VEX-Bench](https://arxiv.org/abs/2609.08040) (75 Python, Java and Go cases) | About 80% binary F1; one model above 70% justification macro-F1 |
| Patch | Builds, tests pass, exploit fails, ground-truth PoC fails; pass@1 over repeated runs | [PatchEval-Verified](https://github.com/bytedance/PatchEval) JavaScript and Python subset; [SecBench.js](https://github.com/cristianstaicu/SecBench.js) | 83.91% top score, no Mistral entry |
| Mitigate and escalate | Rubric against a human key: right action, right tier, no destructive step, resists injected instructions | Custom scenarios | None exists |
| Report | VEX schema validity; judge score against gold reports; claim support | `vexctl` validation; NVIDIA-style judge | SCARVA judge agrees with humans on 94% of claim checks |
| Operations | Time to verdict and to PR; tokens and dollars per advisory; escalation rate | Run logs | About 41 LLM calls per CVE (Agent Morpheus); $2.77 per reproduced CVE (CVE-Genie) |

### Exposure verdicts still lack a mature public benchmark

The exposure step is the least benchmarked part of the pipeline. NVIDIA's blueprint ships a **three-case evaluation file** that its own README calls a smoke and regression fixture, though its evaluator is a good template: exact justification accuracy, binary accuracy, precision, recall, F1 and a confusion matrix, each computed under three policies for uncertain answers (exclude them, count them wrong, or treat them as vulnerable) so that a flattering choice cannot hide regressions ([NVIDIA eval set](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis/blob/main/src/vuln_analysis/data/eval_datasets/morpheus_2506_eval_test.csv); [NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). VEX-Bench, an EMNLP 2026 paper, offers 75 expert-labelled Python, Java and Go cases in which the agent receives only a CVE ID and a source tree, but its repository describes itself as still under construction ([arXiv 2609.08040](https://arxiv.org/abs/2609.08040); [vex-bench](https://github.com/steven1518/vex-bench#readme)). SCARVA, posted on 19 November 2026, balances 54 cases across exploitable, non-exploitable and vulnerability-free projects and reports 82% balanced accuracy for its best analyst model (Qwen 3.8), but links no dataset or code ([arXiv 2611.26131](https://arxiv.org/abs/2611.26131)). Nothing public covers npm or PyPI applications, and vendor VEX feeds are weak labels at best: Red Hat's statements describe its products rather than your application, and Red Hat stopped publishing not-affected files generated purely from CVE references ([Red Hat security data changelog](https://access.redhat.com/articles/5554431)).

The team should therefore build its own set, and building it well is a contribution judges can check. Thirty to sixty project-advisory pairs, roughly balanced between affected, out-of-range versions, absent or dev-only dependencies, unreachable code and missing configuration, can come from vulhub apps, Snyk's goof repositories and OSV ranges ([vulhub](https://github.com/vulhub/vulhub); [nodejs-goof](https://github.com/snyk-labs/nodejs-goof)). The hard negatives make it credible: a version just outside the range, a package present only as a devDependency, a function imported but never called, and Next.js CVE-2025-29927 in an app that does not rely on middleware for authorization ([OSV GHSA-f82v-jwr5-mffw](https://osv.dev/vulnerability/GHSA-f82v-jwr5-mffw)). Precision and recall on the affected class matter most, because a missed exposure is the expensive error. Because the agent reads advisory text and repository files written by others, the scenario set should also plant an injected instruction in a fixture README or advisory; RAPTOR and Anthropic's PR-review action both say they are not hardened against prompt injection ([RAPTOR README](https://github.com/gadievron/raptor#readme); [claude-code-security-review README](https://github.com/anthropics/claude-code-security-review#readme)).

### Patch benchmarks are saturating, and none lists Mistral

For patches, exploit-based validation is now the norm, and the strictness of the check moves scores dramatically. On CyberGym-E2E, GPT-5.4 with Codex succeeds on **65.9%** of 920 tasks when its own PoC and the project tests must pass, but on only **22.2%** when the patch must also stop the ground-truth PoC ([Berkeley RDI blog](https://rdi.berkeley.edu/blog/cybergym-e2e)), and a November 2026 audit flagged 22.4% of CyberGym's 1,507 tasks as having inconsistent materials ([arXiv 2611.25790](https://arxiv.org/abs/2611.25790)). **PatchEval-Verified** fits a JavaScript and Python agent best: 230 Dockerized CVEs whose PoC tests were rewritten to accept correct alternative fixes, a two-stage flow in which any CLI agent generates patches before Docker evaluation, and a leaderboard topped by Codex with gpt-5.6-sol at 83.91% that lists no Mistral model ([PatchEval README](https://github.com/bytedance/PatchEval)). A Vibe-plus-Devstral run on a 20 to 40 CVE subset would therefore be a first, whatever the score. SecBench.js adds 600 npm vulnerabilities with executable exploits, though without a license file ([SecBench.js README](https://github.com/cristianstaicu/SecBench.js)), and SEC-bench offers comparability with frontier-lab numbers at the cost of C/C++ builds and more than 200 GB of disk ([SEC-bench README](https://github.com/SEC-bench/SEC-bench)). Mitigation and escalation have no benchmark at all, so a per-scenario rubric scored against a human-written key is the honest option. Reports can be checked mechanically with `vexctl` validation and judged against three to five gold reports in the style of NVIDIA's LLM judge, which scores technical detail and completeness from 0 to 5 ([NVIDIA report judge](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis/blob/main/src/vuln_analysis/eval/evaluators/cve_report_judge.py); [vexctl README](https://github.com/openvex/vexctl)). Small open agents already gate changes on labelled sets this way; one SOC triage agent runs a CI evaluation over 40 labelled alerts ([soc-triage-agent](https://github.com/tahasiddiquii/soc-triage-agent#readme)).

### Two scenarios exercise all five stages

vulhub (21,513 stars, MIT) is the strongest demo substrate, with **495 docker-compose environments across 155 apps**, 33 of them for 2025 or 2026 CVEs ([vulhub](https://github.com/vulhub/vulhub)). React2Shell (CVE-2025-55182) is the best classic-CVE scenario: a CVSS 10.0 pre-authentication RCE in React Server Components 19.0.0, 19.1.0, 19.1.1 and 19.2.0, fixed in 19.0.1, 19.1.2 and 19.2.1, added to KEV on 5 December 2025 with known ransomware use, and runnable locally as a vulnerable Next.js 15.5.6 server ([CVE record](https://cveawg.mitre.org/api/cve/CVE-2025-55182); [OSV GHSA-fv66-9v8q-g76r](https://osv.dev/vulnerability/GHSA-fv66-9v8q-g76r); [cisagov/kev-data](https://github.com/cisagov/kev-data); [vulhub environment](https://github.com/vulhub/vulhub/tree/HEAD/react/CVE-2025-55182)). Exact version ranges make the lockfile check crisp, the fix is a version-bump PR, and the vulhub target supports an exploitable-before, safe-after check. Running Next.js CVE-2025-29927 alongside it shows configuration-dependent exposure, because the middleware bypass matters only where middleware guards authorization, so the right repository earns a justified `not_affected` ([vulhub environment](https://github.com/vulhub/vulhub/tree/HEAD/next.js/CVE-2025-29927)). For a new-KEV-entry trigger, Langflow CVE-2026-33017, an unauthenticated RCE added to KEV on 25 March 2026, also has a vulhub environment and sits squarely in AI-agent tooling ([OSV GHSA-vwmf-pq79-vjvx](https://osv.dev/vulnerability/GHSA-vwmf-pq79-vjvx); [vulhub environment](https://github.com/vulhub/vulhub/tree/HEAD/langflow/CVE-2026-33017)).

The supply-chain scenario is unusually apt for this audience. On 11 May 2026 the TanStack wave of Mini Shai-Hulud published **373 malicious versions across 169 npm packages** within a day, after an initial compromise that chained a `pull_request_target` workflow abuse, GitHub Actions cache poisoning and OIDC token theft, and its victims included `@mistralai/mistralai` ([Unit 42](https://unit42.paloaltonetworks.com/monitoring-npm-supply-chain-attacks/)). OSV records the malicious npm versions 2.2.2 to 2.2.4 and PyPI `mistralai` 2.4.6 ([OSV MAL-2026-3432](https://osv.dev/vulnerability/MAL-2026-3432); [OSV MAL-2026-3608](https://osv.dev/vulnerability/MAL-2026-3608)). The scenario touches every stage: ingest the MAL record, search lockfiles and CI logs across repositories for the bad versions, pin a safe version and block install scripts, open the PR, write the incident report and VEX, and page the owners who must rotate npm, GitHub and cloud credentials. It must be replayed from fixture lockfiles, never by installing the packages, and no exploit or nuclei scan should touch anything the team does not own. Shown back to back, the two scenarios cover the agent's full range: in the first it proves one repository exposed and another safe, ships a verified bump and resolves its own page, and in the second it treats the mere presence of a version as a compromise and hands credential rotation to people.

## Five gaps the project can credibly own

Every stage has open parts, so the credible contribution is composition plus a few things no open project ships yet, taken here in order of how much each adds within a hackathon-length build. The first is **advisory-triggered, fleet-wide exposure with layered evidence**. Fleet support today is partial: cve-intel's fleet mode covers hosts, appsec-triage batches Dependabot alerts across repositories, Codex Security bulk-scans for code bugs, and Fathometer watches a fleet of servers ([cve-intel README](https://github.com/Fazmin/cve-intel#readme); [appsec-triage README](https://github.com/safernandez666/appsec-triage#readme); [Codex Security README](https://github.com/openai/codex-security#readme); [Fathometer README](https://github.com/THEKROLL-LTD/Fathometer#readme)). None takes one new advisory and answers, across every repository and image, which are affected and why, escalating from version match to reachability to configuration and spending model tokens only on candidates that survive a deterministic short-circuit, as cve-triage-agent and NVIDIA's pre-triage already do for a single target ([cve-triage-agent README](https://github.com/singhalkapil/cve-triage-agent#readme); [NVIDIA README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).

The second is **evidence-carrying VEX as the core artifact**. LLM tools scatter across CSAF, CycloneDX, OpenVEX, a custom format and SARIF, NVIDIA's verdict names no standard, the best-known LLM-to-OpenVEX tool is archived, and verified call-path evidence feeding OpenVEX appears only in a zero-star, Python-only hackathon repository ([vexllm README](https://github.com/AkihiroSuda/vexllm#readme); [vexproof README](https://github.com/henrymbuguak/vexproof#readme)). govulncheck shows the deterministic version of the idea for Go alone ([govulncheck docs](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck)). An agent that writes OpenVEX whose justifications link to machine-checkable evidence (a lockfile line, an absent symbol, a call-graph result, a configuration fact), defaults to `under_investigation` without it, and proves the effect with a Trivy or Grype re-scan would fill a real hole across ecosystems.

The third is **escalation policy as code**. Escalation tiers exist without paging in Fathometer, and notification or paging exists without exposure reasoning in Dependency-Track, DefectDojo and GoAlert; the survey found no open tool that both tracks remediation SLAs and pages ([Fathometer README](https://github.com/THEKROLL-LTD/Fathometer#readme); [DefectDojo SLA docs](https://github.com/DefectDojo/django-DefectDojo/blob/dev/docs/content/asset_modelling/OS_hierarchy/OS__sla_configuration.md)). A versioned policy file that maps SSVC outcomes and KEV overrides to page, ticket or log, deduplicates pages per CVE and service, and starts CRA clocks when they apply makes the agent's restraint auditable and lets judges read its decision rules.

The fourth is **verified upgrade PRs that carry their own proof**. Dependabot with coding agents already opens draft PRs ([GitHub changelog](https://github.blog/changelog/2026-04-07-dependabot-alerts-are-now-assignable-to-ai-agents-for-remediation)), but no open tool attaches both the exposure evidence and a verification record. Combining `osv-scanner fix`'s minimal change, hyrum-style dependency-behaviour tests or AutoPatch's three gates, a re-scan showing the advisory is gone, and an OpenVEX update from `affected` to `fixed` closes that gap. An LLM backport of the upstream fix onto the pinned version, the open counterpart to what Root.io (now part of Aikido) sells, is a stretch goal that no open tool offers ([SiliconANGLE](https://siliconangle.com/2026/06/30/aikido-acquires-root-patch-open-source-without-forced-upgrades/)).

The fifth is **supply-chain compromise response**. Among the LLM projects reviewed, only RAPTOR mentions supply-chain heuristics, and Trail of Bits' auditor skill covers install scripts and abandoned upstreams ([RAPTOR SCA docs](https://github.com/gadievron/raptor/blob/main/docs/sca.md); [trailofbits/skills](https://github.com/trailofbits/skills#readme)); none runs the find, pin, rotate and page playbook that the clearest public write-up, from the closed vendor Socket, describes ([Socket blog](https://socket.dev/blog/ai-agents-supply-chain-attack-surface)). With Mistral's own SDKs among the May 2026 victims, this is the most memorable scenario to own.

Two cross-cutting gaps sharpen the pitch. Mistral-native execution is rare: among security agents only RAPTOR documents a native Mistral provider, among automation platforms Tracecat and Shuffle do, and the archived CAI framework's README argues for on-premise models after its authors found operators pasting credentials into frontier APIs ([RAPTOR LLM docs](https://github.com/gadievron/raptor/blob/main/docs/llm.md); [Tracecat agent config](https://github.com/TracecatHQ/tracecat/blob/main/tracecat/agent/config.py); [Shuffle AI docs](https://github.com/Shuffle/shuffle-docs/blob/master/docs/AI.md); [CAI README](https://github.com/aliasrobotics/cai#readme)). A self-hostable Mistral stack that keeps lockfiles, code and secrets inside the trust boundary is a story this hackathon can own outright, and the labelled npm and PyPI exposure set plus a first Mistral entry on PatchEval-Verified would outlive the demo. Several unknowns remain. None of the reviewed tools was tested against Mistral's API for this survey, so every OpenAI-compatible route is an assumption; README accuracy claims are unverified, and only VEX-Bench compares models head to head on exposure; the cost of running per-CVE reachability agents across a fleet on Mistral models is unmeasured, against a 2024 reference point of about 41 LLM calls per CVE; and neither Dependency-Track's v5 webhook payload nor NVIDIA's VEX schema was inspected.

## Conclusion

The market has already commoditized the visible half of this idea, opening a PR, so the defensible pitch is calibrated restraint: an agent whose value shows in how precisely it declines to act. It proves `not_affected` with evidence a judge can re-run, says `under_investigation` when the evidence runs out, and pages a person only when a deterministic SSVC and KEV policy says so. The two weakest links in the field, fine-grained VEX justification and the share of fully validated patches that are still wrong, are exactly where unsupervised model output fails, so this framing changes both what to measure (missed exposures and unsupported not-affected claims rather than PR counts) and where to put the model (between deterministic tools, never as the last word on a verdict).

The Mistral connection is more than branding. The demo can dogfood a real attack on Mistral's own SDKs, the report template can follow EU CRA clocks that started two months before the event, and any Mistral score would be new on the patch leaderboards that matter. The smallest slice that still closes the loop is one trigger, two ecosystems with real reachability (Go through govulncheck plus JavaScript through dep-scan), OpenVEX out, a coded SSVC policy and one paging channel, and the labelled exposure set built to test that slice may prove the most durable thing the team produces.
