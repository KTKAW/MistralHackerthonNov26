# Open-source LLM/agentic projects for end-to-end vulnerability response (closest prior art to a "security incident response agent")

Scope: open-source GitHub projects that use LLMs or agents to triage a new CVE/advisory, decide whether a codebase/SBOM/image is actually exposed or exploitable, remediate, and report/escalate. Closed products appear only as context in Q4 and are marked **[CLOSED]**. Non-LLM scanners/feeds, deterministic patch bots, SOAR/escalation tooling and benchmarks are covered by other researchers; they appear here only where a covered project integrates them.

Verification method (applies to every repo listed): metadata was pulled with `gh api repos/OWNER/REPO --jq '{full_name,stargazers_count,pushed_at,license:.license.spdx_id,archived,description}'` on **2026-11-21**. Stars and dates below are exactly what the API returned that day. A few star counts moved by 1 between two calls on the same day (e.g. openai/codex-security 14238 then 14239); the later value is recorded. "Stale" = no push in 12+ months (before 2025-11-21). Stage codes: **I** = ingest signal, **A** = assess exposure/exploitability, **M** = mitigate/patch, **R** = report (incident report/VEX), **E** = escalate.

## Q1. Which open-source projects already implement CVE-driven exposure or exploitability analysis with LLM agents? (verified inventory)

### Takeaway
Only a handful of maintained OSS projects take a CVE/advisory as input and decide exposure for *your* artifact with an LLM in the loop. The most complete are NVIDIA's Vulnerability Analysis blueprint (container + CVE/GHSA → evidence-backed VEX, no patching), RAPTOR (SCA with mechanical reachability, CycloneDX VEX, a fix planner and native Mistral support) and OWASP dep-scan (deterministic reachability plus CSAF VEX, now with an MCP server and agent skills). Around them sit smaller LLM VEX and triage tools (OWASP Xpsd, vexllm (archived), vens, Fathometer, cve-intel) and LLM remediation agents (Patchwork, Codex Security CLI, Visa VVAH, Google Mantis). **None covers the whole ingest → assess → patch → VEX report → escalate loop.** Several very small repos pushed in October–November 2026 are attempting this loop, two of them explicitly as Meta hackathon entries. That shows the idea is current and that the space is crowded.

#### A. CVE/advisory-driven exposure and exploitability analysis (closest prior art)

**1. NVIDIA-AI-Blueprints/vulnerability-analysis** ("Vulnerability Analysis for Container Security", successor to "Agent Morpheus")
- Repo: https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis. Python, Apache-2.0, 255★, last push 2026-11-12, not archived ([gh api](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis)). NVIDIA services/models used with it "may have additional governing terms" ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- Purpose: decide whether documented CVEs are exploitable in a specific container image and publish a reviewable VEX decision ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- Current design: a three-stage multi-agent LangGraph workflow on the NeMo Agent Toolkit. Stage 1 runs a **CVE Researcher** (AI-Q DeepAgents, web-only tools; an advisory sub-researcher plus an exploit-intelligence sub-researcher covering KEV, EPSS and public PoCs) in parallel with a **Container Analyzer** (rootfs tools limited to read/list/grep/glob). Stage 2 is the **Exploitability Analyzer**; Stage 3 is the **VEX Categorizer** ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- Inputs: JSON `PipelineInput` with one or more `vuln_id` (CVE or GHSA, with optional package/version hints) and `image_name` + `image_tag`, or a pre-extracted rootfs. The image is pulled and flattened with `crane` ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). It does not include the scanner that discovers the CVEs; that comes from upstream tools such as Anchore ([NVIDIA build catalog](https://build.nvidia.com/nvidia/vulnerability-analysis-for-container-security)).
- Outputs: Markdown reports (vulnerability, container, exploitability) and a VEX decision per vulnerability–image pair as Markdown plus a JSON sidecar. Status is `affected`/`not_affected` (or fail-safe `unknown`/`uncertain`), with justifications such as `code_not_present`, `code_not_reachable`, `requires_configuration`, `requires_dependency`, `requires_environment`, `compiler_protected`, `runtime_protected`, `perimeter_protected`, `mitigating_control_protected` or `vulnerable` ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- Interfaces: `vuln-analysis preflight` / `run-pipeline` CLI, `nat run`, and a FastAPI service with OpenAPI, async jobs, report-download endpoints, optional OAuth2/JWT, and terminal webhooks with HMAC signing ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- Limitations: containers only. Needs NVIDIA NIM (or a compatible endpoint) plus a Tavily key. Needs at least 20 GiB of disk for the quick start. The checked-in evaluation set is only 3 reviewed cases, which NVIDIA calls "not a statistically representative benchmark". No patching or ticketing ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). The README never says that the VEX JSON follows OpenVEX, CSAF or CycloneDX (grep of README; see Gaps).
- History (Agent Morpheus, May 2024): a LoRA-fine-tuned Llama 3 planner generated a per-CVE **checklist**. An agent executed it with SBOM search, source code search, documentation, internet search and a version-comparison tool, and a separate model standardized the VEX justifications. It used about 41 LLM queries per CVE and gave a 9.3× speedup on a 20-CVE container (2842 s serial vs 305 s parallel). Analysts and peer review approved results before the VEX was published, and analyst edits were fed back as training data ([NVIDIA tech blog, 2024-05-23](https://developer.nvidia.com/blog/applying-generative-ai-for-cve-analysis-at-an-enterprise-scale/)).
- Reuse for a hackathon: run it as the "assess" microservice behind your agent through its REST API, or lift its decision policy (association → code presence → execution path → trigger conditions → protective controls) and its fail-safe `unknown` handling into Mistral prompts. Per-role model environment variables make substitution possible ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).

**2. gadievron/raptor** (Recursive Autonomous Penetration Testing and Observation Robot)
- Repo: https://github.com/gadievron/raptor. Python, 4042★, last push 2026-11-21, not archived. API license is `NOASSERTION`, but the README says "MIT -- Copyright (c) 2025-2026 Gadi Evron, Daniel Cuthbert, Thomas Dullien (Halvar Flake), Michael Bargury, John Cartwright" ([gh api](https://github.com/gadievron/raptor); [README](https://github.com/gadievron/raptor#readme)).
- Purpose: an autonomous security research framework built on Claude Code (though not tied to it). It chains static/binary analysis, LLM validation, exploit generation and patch writing ([README](https://github.com/gadievron/raptor#readme)).
- CVE-exposure relevance: the `/sca` workflow extracts dependencies and matches them against OSV, CISA KEV and EPSS (plus Vulnrichment SSVC). It runs **two-tier reachability**: module/package imports, then function-level reachability when the advisory names affected symbols. Verdicts are `likely_called`, `imported`, `not_function_reachable`, `not_reachable`, `called_in_dead_code` and `not_evaluated`. It writes a CycloneDX 1.5 SBOM with a VEX block by default, plus SARIF ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)).
- Remediation: `raptor-sca fix` shows or applies a fix plan (`--apply`, `--cve-only`, `--allow-major`, `--no-llm`). `raptor-sca upgrade <eco> <name> <from> <to>` reports the advisories an upgrade resolves versus introduces ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)). `/agentic` generates "PoCs and patches for review" for code findings ([README](https://github.com/gadievron/raptor#readme)).
- Interfaces: Claude Code slash commands (`/agentic`, `/sca`, `/validate`, `/binary`, `/oss-forensics`…) and a standalone CLI (`python3 raptor.py sca --repo … --no-llm`, `bin/raptor-sca`) ([README](https://github.com/gadievron/raptor#readme); [docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)).
- Limitations: "not polished software… held together with enthusiasm and duct tape" and "mostly AI-generated code" ([README](https://github.com/gadievron/raptor#readme)). Reachability verdicts are "triage signals, not… mathematical proof", and SBOM-only scans cannot prove reachability ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)). "Prompt injection remains possible" ([README](https://github.com/gadievron/raptor#readme)).
- Reuse: the strongest OSS building block for the "assess + plan fix + VEX" stages, and it already supports Mistral natively (Q3). Wrap `raptor-sca` as a tool, use its VEX/SARIF output, and borrow its sandbox (Landlock/seccomp/Seatbelt) design ([README](https://github.com/gadievron/raptor#readme)).

**3. owasp-dep-scan/dep-scan** (OWASP; non-LLM core with an agent interface)
- Repo: https://github.com/owasp-dep-scan/dep-scan. Python, MIT, 1462★, last push 2026-11-20, not archived ([gh api](https://github.com/owasp-dep-scan/dep-scan)).
- Purpose: scan source repos, container images, Kubernetes manifests and OSes for known CVEs with prioritization. It runs reachability for seven ecosystems (atom for JVM/JS/Python/PHP, rusi for Rust, golem for Go, dosai for .NET) and generates a CycloneDX SBOM/VDR and **CSAF 2.0/2.1 VEX** ([README](https://github.com/owasp-dep-scan/dep-scan#readme)).
- LLM-related features: an `--explanation-mode LLMPrompts` option ([README](https://github.com/owasp-dep-scan/dep-scan#readme)). A coding-agent plugin ships 14 Agent Skills (e.g. `depscan-scan`, `depscan-triage`, `depscan-reachability-proof`, `depscan-vex-compliance`, `depscan-container-image`, `depscan-supply-chain`), sub-agents (`vuln-triager`, `exposure-analyst`, `binary-reviewer`), and an MCP config that starts `depscan mcp` ([agent-plugin/README.md](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/README.md); [.mcp.json](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/.mcp.json)). The plugin "ships instructions, not the tool". The vuln-triager "never records a triage decision" because the MCP server has no `record_triage` tool. Install steps are documented for Claude Code, Codex, opencode and ZCode; Cursor, Gemini CLI, Kiro and Copilot CLI are "not yet tested" ([agent-plugin/README.md](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/README.md)).
- Reuse: a deterministic exposure engine plus a standards-compliant VEX writer that a Mistral agent can call over MCP. This lets the LLM focus on judgment and narrative instead of version math.

**4. OWASP/Xpsd** (formerly ByteRay-AI/Xpsd)
- Repo: https://github.com/OWASP/Xpsd. Go, Apache-2.0, 11★, last push 2026-11-04, not archived. The previous home [ByteRay-AI/Xpsd](https://github.com/ByteRay-AI/Xpsd) (18★) is archived and its README points to OWASP ([gh api](https://github.com/OWASP/Xpsd); [ByteRay README](https://github.com/ByteRay-AI/Xpsd#readme)).
- Purpose: "One command that decides whether a reported vulnerability is actually reachable in a given source tree." Input is a CVE description or a whole scan report (Grype, Trivy, OSV-Scanner, Snyk, any SARIF). Output is structured verdicts, Markdown and SARIF for GitHub code scanning ([README](https://github.com/OWASP/Xpsd#readme)).
- Method: an agent with tools instead of whole-repo context: ast-grep for code navigation, OSV.dev lookups and page rendering to fetch the advisory and fixing commit, and dependency fetching for built-not-vendored components. Each alert carries a rationale, the call path from entry point to vulnerable use, and evidence links ([README](https://github.com/OWASP/Xpsd#readme)).
- CI/escalation features: filters `min-severity`, `min-cvss`, `max-findings`, `is-remote` (CVSS AV:N) and `is-exploited` (CVSS-BT). `fail-on: reachable` gates builds. A `guidance` input supplies non-code facts such as what is compiled or network-exposed. Not-reachable findings are lowered to low severity in the Security tab ([README](https://github.com/OWASP/Xpsd#readme)).
- Limitations: one agent session per finding, so cost scales with findings. Defaults to GitHub Copilot billing ([README](https://github.com/OWASP/Xpsd#readme)).
- Reuse: the reachability-agent pattern (tool-based, evidence-linked, SARIF output) maps directly onto stage 2.

**7. THEKROLL-LTD/Fathometer**
- Repo: https://github.com/THEKROLL-LTD/Fathometer. Python, Apache-2.0, 37★, last push 2026-11-21 ([gh api](https://github.com/THEKROLL-LTD/Fathometer)).
- Purpose: self-hosted CVE triage for root servers and VPSes. Trivy agents push results from each host. An LLM "context reviewer" asks whether a finding is reachable on that host, whether the vulnerable code path runs, and whether an attacker can meet the preconditions. CVSS, EPSS and KEV are weights, "never… the verdict". Output tiers are **Escalate · Act · Watch · Noise**, and each downgrade names the missing condition ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
- Extras: separates patches `apt`/`dnf` can actually apply from upstream-only fixes in statically linked binaries. An opt-in agentic "upstream check" searches releases and build manifests. A scoped CVE chat answers questions ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
- Limitations: single-user. Not for images, Kubernetes or CI. Deliberately has "no email / Discord / webhook noise", so no notifications ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
- Reuse: its four-tier taxonomy is a ready-made escalation vocabulary, and its "real vs phantom patch" logic suits host mitigation.

**8. Fazmin/cve-intel**
- Repo: https://github.com/Fazmin/cve-intel. Rust, Apache-2.0 per API (README badge: "MIT OR Apache-2.0"), 151★, last push 2026-11-21 ([gh api](https://github.com/Fazmin/cve-intel); [README](https://github.com/Fazmin/cve-intel#readme)).

**9. Maintainer-side advisory triage: php/tamis and apache/magpie**

### Inferences
- For CVE → "am I exposed?" the realistic OSS base is a hybrid: dep-scan or RAPTOR (deterministic matching, reachability and VEX) plus an LLM agent for advisory reading, ambiguity resolution and narrative. - Most high-star "AI security" repos (Strix, Shannon, Codex Security, VVAH, Mantis, VulnHunter) find *new* bugs in first-party code. They are not advisory-driven response tools, though their verify/patch stages are reusable.

## Q2. How does each project decide exploitability or exposure, and how autonomous is it (where does the human stay in the loop)?

### Takeaway
Four decision styles recur: (1) **deterministic-first, LLM-for-ambiguity** (NVIDIA pre-triage, RAPTOR SCA, dep-scan, singhalkapil, Patchwarden's policy gate); (2) **LLM agent navigating code with tools** and producing call-path evidence (Xpsd, NVIDIA Stage 2, seclab taskflows, Metis, VVAH); (3) **LLM judging from advisory text plus operator context** without code inspection (vexllm, vens, Fathometer, DockSec explanations); and (4) **dynamic proof** via PoC exploits or failing/passing tests (Strix, Shannon, Mantis, AutoPatch, dvalincode, CodeMender (closed)). Almost every project keeps a human approval step before merge or publication. The common pattern is "LLM recommends, deterministic gate or human decides".

### Cited Findings
**Deterministic-first + LLM for ambiguity**
- NVIDIA: "deterministic pre-triage checks installed packages, versions, distribution backports, binaries, and runtime environments. Clear-cut cases are resolved without deep-analysis LLM calls". Ambiguous cases go to an LLM using filesystem, binary, package and security-control tools to examine reachability, attacker-controlled data flow, dependencies and mitigations ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
- NVIDIA human loop: reports are "designed to support analyst review"; for policy gates, "validate the cited evidence"; failures produce `unknown`/`uncertain` instead of being treated as safe ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). The 2024 Agent Morpheus process added analyst plus peer review before VEX publication ([NVIDIA blog](https://developer.nvidia.com/blog/applying-generative-ai-for-cve-analysis-at-an-enterprise-scale/)).
- RAPTOR: "SCA reachability is mechanical. RAPTOR does not ask an LLM whether a dependency is reachable", using AST import parsing and a call graph against advisory-listed functions. LLM review runs later "but it is not the source of truth" ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)). For code findings, `/validate` performs "eight-stage exploitability validation" (reachability, preconditions, mitigations, with dynamic verification where artefacts allow) ([README](https://github.com/gadievron/raptor#readme)). Human: reports "support security research and human review; its reports do not certify that a codebase is secure", and reduced sandbox protection "requires explicit consent" ([README](https://github.com/gadievron/raptor#readme)).
- dep-scan: static slicing (atom/rusi/golem/dosai) marks a package Reachable only when its code is on a traced path ([README](https://github.com/owasp-dep-scan/dep-scan#readme)). The agent plugin's triager never records triage decisions ([agent-plugin/README.md](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/README.md)).
- Patchwarden: "The Claude agent only recommends; a deterministic policy gate decides whether a fix ships automatically or goes to a human". Failed verification routes to human review ([README](https://github.com/deenojo/Vulnerability-Remediation-Agent#readme)).
- PatchTriage: "AI never chooses the SSVC outcome and never invents a score" ([README](https://github.com/d01ki/PatchTriage#readme)). cve-intel runbooks are "made by fixed rules with no AI" ([README](https://github.com/Fazmin/cve-intel#readme)).

**LLM agent navigating code/artefacts with tools**
- Xpsd: an agent using ast-grep, OSV, the fixing commit and dependency fetching. Low-confidence or failed analyses become "warning, needs manual review" ([README](https://github.com/OWASP/Xpsd#readme)).
- seclab taskflows: staged gathering → audit criteria → report validation → issues for human review; "review carefully all generated output"; no dynamic validation ([GitHub blog](https://github.blog/security/ai-supported-vulnerability-triage-with-the-github-security-lab-taskflow-agent/)). The framework can force user confirmation for listed tools ([README](https://github.com/GitHubSecurityLab/seclab-taskflow-agent#readme)).
- VVAH: playbooks with hard gates ("a reachable source, an exploitable sink and no effective defense"), a code graph queried by S2/S4/S6, and an adversarial verifier. Findings "stay triage candidates" for human review ([README](https://github.com/visa/visa-vulnerability-agentic-harness#readme)).
- vulnhuntr: LLM-built call chains from remote input to output, with a confidence score (<7 unlikely, 7 investigate, 8+ very likely) and a PoC ([README](https://github.com/protectai/vulnhuntr#readme)).
- VulnHunter: a "falsification engine" that tries to *disprove* each finding before remediation ([README](https://github.com/capitalone/VulnHunter#readme)).

**LLM judging from advisory text + operator context**
- vexllm: hints such as "not a server program" or used/unused commands steer an LLM that emits `not_affected` with a confidence and reason ([README](https://github.com/AkihiroSuda/vexllm#readme)).
- vens: an LLM produces OWASP likelihood × impact scores from a system-context config ([README](https://github.com/venslabs/vens#readme)).
- Fathometer: the LLM reviewer asks reachability, code-path and precondition questions per host. The "AI advises, you decide"; the agentic upstream check is advisory-only and off by default ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
- appsec-triage: verdicts posted as GitHub Issues; auto-dismiss of false positives is configurable ([README](https://github.com/safernandez666/appsec-triage#readme)).

**Dynamic proof (PoC or tests)**
- Strix validates "through actual proofs-of-concept" ([README](https://github.com/usestrix/strix#readme)); Shannon: "No exploit, no report" ([README](https://github.com/KeygraphHQ/shannon#readme)).
- Mantis reproduces vulnerabilities "to varying degrees" in sandboxes and gates on deterministic verification; "All findings must be manually verified by a security expert" ([README](https://github.com/google/mantis#readme)).
- AutoPatch's verification contract: a regression test fails on vulnerable code, passes after the patch, and the existing suite shows no new failures ([README](https://github.com/Kokenya/autopatch#readme)). dvalincode re-runs scanners and tests, and "No model has a say in the verdict" ([README](https://github.com/arthurpanhku/dvalincode#readme)). VVAH's S11 fix validation "runs no tests" ([README](https://github.com/visa/visa-vulnerability-agentic-harness#readme)).

**Human-in-the-loop by design**
- Magpie: "Every comment, email, label and PR is *drafted* by the agent and posted by a person. There is no autonomous mode" ([README](https://github.com/apache/magpie#readme)). tamis: "The maintainers keep the decision" ([README](https://github.com/php/tamis#readme)).
- Patchwork, Codex Security and the GitHub Action tools (claude-code-security-review, Xpsd) end in PRs, comments or alerts that humans merge or dismiss ([Patchwork README](https://github.com/patched-codes/patchwork#readme); [Codex Security README](https://github.com/openai/codex-security#readme); [CCSR README](https://github.com/anthropics/claude-code-security-review#readme)).
- Tracecat: approval of sensitive tool calls from an inbox, Slack or email is an Enterprise feature ([README](https://github.com/TracecatHQ/tracecat#readme)).

### Inferences
- The more trusted designs never let the LLM produce the *final* "not affected" claim without evidence. They either cap verdicts by provable evidence (FirstWatch, Xpsd's call paths, NVIDIA's reasoning trace) or have deterministic code make the call. A hackathon agent emitting VEX `not_affected` should attach machine-checkable evidence (version ranges, absent symbols, call-graph result) and default to "under investigation" otherwise.
- "Reachability ≠ exploitability" (VEX-Bench framing; NVIDIA's separate trigger-condition and protective-control steps) argues for at least two layers: code reachability, then configuration/deployment conditions.
- Full autonomy appears only at the edges: auto-dismissing obvious false positives (appsec-triage, configurable) and auto-merging policy-approved low-risk bumps (Patchwarden). Mainstream projects stop at draft PRs and human approval.

### Gaps
- No project published a head-to-head accuracy comparison on a common dataset except VEX-Bench (model-level, not tool-level). NVIDIA's own eval has 3 cases. Relative accuracy of these tools is unknown.
- Did not verify how RAPTOR's LLM triage interacts with its mechanical VEX (e.g. whether LLM output can change a VEX status); the docs only say the LLM is "not the source of truth".

## Q5. What gaps remain that a hackathon project could credibly fill?

### Takeaway
The open gap is a **single open-source, model-agnostic (Mistral-native) agent that closes the whole loop**:
1. Event-driven ingestion of new advisories (CVE/GHSA/OSV, KEV additions, supply-chain compromises).
2. Fleet-wide "which of our repos/images/hosts are affected" with layered exposure evidence (version → reachability → config/deployment).
3. Verified patch PRs.
4. Standards-compliant VEX plus an incident report with evidence.
5. A policy-as-code escalation to Slack/PagerDuty/Jira.

Existing OSS pieces cover each stage separately (dep-scan/RAPTOR for exposure+VEX, NVIDIA for deep container analysis, Xpsd for reachability evidence, AutoPatch/dvalincode/hyrum for verification, cve-intel/Fathometer for fleets and tiers), so a hackathon team can credibly *compose* rather than invent.

### Cited Findings
- Stage coverage evidence:
  - NVIDIA stops at VEX and reports, plus a completion webhook, with no patching ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
  - RAPTOR has SCA, a fix planner and VEX but no advisory-feed watcher or paging (from its README/docs feature lists; [docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)).
  - Fathometer has escalation tiers but explicitly no notifications ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
  - cve-intel has a fleet, VEX and webhooks but no PRs (runbooks only) ([README](https://github.com/Fazmin/cve-intel#readme)).
  - WaarlandIT cve-agent covers NVD poll → assess → report → Slack without patching ([README](https://github.com/WaarlandIT/cve-agent#readme)).
  - Patchwarden covers scan → triage → policy gate → PR/Copa → verify, without VEX or paging ([README](https://github.com/deenojo/Vulnerability-Remediation-Agent#readme)).
- VEX format fragmentation:
  - CSAF VEX in dep-scan ([README](https://github.com/owasp-dep-scan/dep-scan#readme)).
  - CycloneDX VEX in RAPTOR ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)) and vens ([README](https://github.com/venslabs/vens#readme)).
  - OpenVEX in vexllm (archived) ([README](https://github.com/AkihiroSuda/vexllm#readme)) and cve-intel ([README](https://github.com/Fazmin/cve-intel#readme)).
  - A custom Markdown/JSON VEX decision in NVIDIA ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)).
  - SARIF, not VEX, in Xpsd ([README](https://github.com/OWASP/Xpsd#readme)).
- Fine-grained justification is the hard part: in VEX-Bench, frontier agents reach about 80% F1 on affected/not-affected, but only one model exceeds 70% macro-F1 on justification categories ([arXiv:2609.08040](https://arxiv.org/abs/2609.08040)).
- Reachability is necessary but not sufficient. NVIDIA separately evaluates trigger conditions and protective controls ([README](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis#readme)). Xpsd notes reachability "depends on facts that are not in the code" and asks for them via `guidance` ([README](https://github.com/OWASP/Xpsd#readme)).
- Verification building blocks exist separately: the AutoPatch 3-gate contract ([README](https://github.com/Kokenya/autopatch#readme)), the dvalincode Verified Fix Record ([README](https://github.com/arthurpanhku/dvalincode#readme)), hyrum dependency-behaviour tests ([README](https://github.com/alpha-omega-security/hyrum#readme)), and Trail of Bits `patching-bugs`/`post-patch-validation` skills ([README](https://github.com/trailofbits/skills#readme)).
- Fleet/multi-repo support is partial: cve-intel fleet mode (hosts) ([README](https://github.com/Fazmin/cve-intel#readme)), appsec-triage `--repos` batch ([README](https://github.com/safernandez666/appsec-triage#readme)), Codex Security bulk scans (code vulns) ([README](https://github.com/openai/codex-security#readme)), Fathometer host fleet ([README](https://github.com/THEKROLL-LTD/Fathometer#readme)).
- Supply-chain compromise response: among the LLM projects reviewed, only RAPTOR mentions supply-chain heuristics (LLM typosquat triage) ([docs/sca.md](https://github.com/gadievron/raptor/blob/main/docs/sca.md)), and Trail of Bits' auditor covers install scripts and abandoned upstreams ([README](https://github.com/trailofbits/skills#readme)). The incident-style playbook Socket advises after an npm worm (remove packages, delete node_modules, rotate npm/GitHub/CI secrets, review AI assistant configs) is described by a closed vendor ([Socket blog](https://socket.dev/blog/ai-agents-supply-chain-attack-surface)), not implemented by an OSS LLM agent found here.
- Mistral-native support is rare: documented natively only in RAPTOR ([docs/llm.md](https://github.com/gadievron/raptor/blob/main/docs/llm.md)) and Tracecat ([config.py](https://github.com/TracecatHQ/tracecat/blob/main/tracecat/agent/config.py)).

### Inferences
(Ranked by credibility for a 1–2 day build.)
1. **Advisory-triggered, fleet-wide "am I affected?" with layered evidence.** Ingest one signal (e.g. a KEV addition or GHSA), enumerate affected repos/images through SBOMs (dep-scan or RAPTOR over MCP), then run an LLM reachability/config check (Xpsd-style tools) only on candidates. This combines the cheap deterministic short-circuit (singhalkapil, NVIDIA pre-triage) with LLM depth where it matters.
2. **Evidence-carrying OpenVEX (or CSAF) as the core artifact.** Each statement would link versions, call-path or absent-symbol evidence, and config facts, defaulting to `under_investigation` when evidence is missing. No maintained OSS LLM tool emits OpenVEX with attached evidence (vexllm is archived; NVIDIA's format is custom).
3. **Escalation policy as code.** For example, `KEV ∧ reachable ∧ internet-facing → PagerDuty; affected ∧ no fix → Jira + Slack; not_affected → VEX only`, borrowing Fathometer's Escalate/Act/Watch/Noise or SSVC outcomes (PatchTriage, singhalkapil). Today these tiers exist without paging, or paging exists without exposure reasoning.
4. **Verified patch PRs for CVE-driven upgrades.** Minimal bump, hyrum-style dependency tests or the AutoPatch 3-gate contract, then a re-scan that proves the CVE is gone. Commodity PR bots (Dependabot plus agents) don't present evidence of exposure *and* verification together.
5. **Supply-chain compromise playbook** (malicious version published): find the version in lockfiles and images across the fleet, pin or roll back, open PRs, list secrets to rotate, and page owners. This is a visible demo scenario that no OSS LLM agent found here handles.
6. **Mistral-native, self-hostable execution** (data stays in the trust boundary). For example, a larger Mistral model for reasoning and a code model for patches. CAI's archive explicitly argues for on-premise models after finding operators pasting credentials into frontier APIs ([CAI README](https://github.com/aliasrobotics/cai#readme)). This is a narrative a Mistral-hackathon team can own.
- Reuse map for the build: ingest via cve-intel/vulnify/osv-mcp MCP servers. Assess via dep-scan MCP or `raptor-sca` (native Mistral) plus an Xpsd-style reachability agent. Patch via Patchwork steps, RAPTOR fix planner or Copa (as Patchwarden does). Verify via dvalincode/hyrum/AutoPatch-style gates. Report via dep-scan CSAF or a hand-rolled OpenVEX, using NVIDIA's justification taxonomy. Orchestrate via seclab-taskflow-agent YAML (OpenAI-compatible endpoint) or Tracecat (native Mistral). Licenses differ (AGPL-3.0 for Patchwork, Tracecat, Shannon and Buttercup; CC-BY-SA for Trail of Bits skills; none for Patchwarden and appsec-triage), which matters if the result is published.
